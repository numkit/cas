# Модель интеграции в Numkit (обсуждение 2026-09-06)

Статус: интеграция отложена до готовности ядра (минимум C1), но контракт
совместимости обязателен для всего кода с первого дня — ретрофит этих
решений стоит на порядки дороже.

## Установленные факты о Numkit (по результатам разбора репозитория)

- Строго C++17 (`CMAKE_CXX_STANDARD 17`, `cxx_std_17` PUBLIC). Нет
  `jthread`/`stop_token`/`concepts`/`format` — отмена каскада через свой
  лёгкий бюджет-токен.
- Нулевые внешние зависимости у движка; WASM-сборка через emsdk
  (`-fexceptions` включён). Значит: свой `BigInt` обязателен (Boost/GMP
  исключены), никаких внешних либ в библиотечном коде.
- Движок однопоточный → спекулятивный параллелизм D9 плана переезжает в
  «опцию потом»: каскад сначала последовательный с таймбоксами фаз.
- Память — PMR (`std::pmr` в Value/HeapObject). Арена/hash-consing ядра
  должны сидеть на `memory_resource`.
- Лицензия Numkit — 0BSD. Вопрос LGPL/FLINT из плана (§11) закрыт сам
  собой: FLINT не используется. Правила Rubi (MIT) совместимы с
  атрибуцией.
- Точка расширения для символьных значений уже спроектирована в Numkit:
  `BuiltinClass` с `NativePayload` (object.hpp; прецеденты — containers.Map,
  table). `sym` — BuiltinClass, в payload — хэндл интернированного
  выражения + контекст.
- Культура: 4 артефакта на публичную функцию (реализация, parity-спека
  против MATLAB R2025b, gtest, smoke), полный корпус дорогой (~5 мин).

## Четыре слоя интеграции

1. **Ядро CAS** (этот репозиторий): ничего не знает об интерпретаторе.
2. **Вендоринг**: исходники ядра синхронизируются скриптом в
   `src/toolboxes/symbolic/cas/` внутри Numkit (единая статическая сборка;
   динамическая линковка для WASM мертва). Раскладка
   `include/numkit/cas/**` уже совпадает с целевой.
3. **Адаптер значений**: `sym` через BuiltinClass + NativePayload.
4. **Скриптовая поверхность**: паритет с MATLAB Symbolic Math Toolbox
   (`syms`, `sym`, `int`, `diff`, `simplify`, `subs`, `vpa`, `solve`,
   `taylor`, `limit`...) по правилу full-fidelity.

Нюанс: `library_api.md` §0 в Numkit сейчас выводит объектные функции из
скоупа тулбоксов — символьный тулбокс будет первым объектоцентричным,
нужно санкционированное расширение правила, когда дойдём.

## Решение: выражения входят через значения, а не через AST (2026-09-07)

AST интерпретатора Numkit НЕ используется для построения символьных
выражений. Путь: обычное call-by-value вычисление + перегрузка операций
на `sym`-объекте (BuiltinClass + NativePayload с хэндлом Expr) — как в
самом MATLAB SMT. Мотивация:

1. Паритет с MATLAB (правило full_fidelity).
2. Нулевая хирургия интерпретатора: ленивая передача AST (fexpr-стиль)
   потребовала бы зеркальных расширений TreeWalker И VM — риск
   dual-engine расхождений. Путь значений в обоих движках работает
   одинаково автоматически.
3. Контракт вендоринга: ядро не знает об интерпретаторе.
4. Ловушка числовых литералов не решается AST-путём в принципе: лексер
   Numkit делает из `1/2` double ДО любого обхода AST. Решение на
   значениях, как в MATLAB: dyadic-даблы → Rational точно; не-dyadic —
   через строковый конструктор sym('1/10').

Собственный парсер в CAS всё равно нужен (строчный конструктор,
standalone-CLI, корпус §7 — текстовые файлы) — pratt-парсер, напрямую
вызывающий конструкторы Ctx, без промежуточного AST-типа.

Пересмотреть решение, если появятся: конвертация function handles в
символьные формы, ленивые выражения.
